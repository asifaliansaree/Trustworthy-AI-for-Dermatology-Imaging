# Week 4 — Grad-CAM & First Heatmaps

## Decisions made

### Why Captum's `LayerGradCam` instead of a hand-rolled hook implementation
Captum gives a tested, maintained Grad-CAM implementation with the same
API surface as the other three attribution methods planned for Week 5
(`Saliency`, `IntegratedGradients`, `Occlusion`). Writing all four methods
against one library means `compare_methods.py` (Week 5) can call them
interchangeably instead of reconciling four different attribution formats.

### Why `layer4[-1].conv2` as the target layer
`DermaNet`'s backbone is stored as an `nn.Sequential` of
`(conv1, bn1, relu, maxpool, layer1, layer2, layer3, layer4, avgpool)`.
`avgpool` is index `-1`, which makes `layer4` index `-2` — not `-3`, which
is `layer3`. Getting this off by one silently produces a heatmap from the
wrong resolution stage (28×28 instead of 7×7 feature maps), which still
*looks* plausible after upsampling but is attributing to the wrong depth
of the network. This is called out explicitly in `gradcam.py` to stop it
from being re-broken later.

> **Update (Week 6):** with the migration to ResNet-50 (Bottleneck blocks,
> not BasicBlock), the last conv in `layer4[-1]` is `conv3`, not `conv2`.
> `get_target_layer()` now detects this via `hasattr(last_block, "conv3")`
> instead of hardcoding the attribute name, so the same function is correct
> for both architectures without needing to be touched again on a future
> backbone swap.

### Why heatmaps are split into `correct/` and `failures/` folders
The synopsis Week 4 task is explicitly "visualise attributions on correct
vs incorrect cases" — keeping them in separate folders (rather than one
folder with correctness encoded only in the filename) makes it possible to
eyeball the two populations side by side without cross-referencing the CSV.

### Why the failure heatmaps run against `xai_target_cases.json` from Week 3
Using the same fixed, pre-saved list of 20 high-confidence wrong
predictions (rather than re-mining new failures now) keeps every XAI
method in Weeks 4–9 auditing the *same* cases, so results are directly
comparable across methods and across weeks.

## Key findings

- Ran Grad-CAM on the locked `v0.1-baseline` checkpoint (epoch 15,
  val_bal_acc 0.7964), producing **13 heatmaps for correctly-classified
  cases** and **20 heatmaps for the fixed Week 3 failure list**.
- The 20 failure cases split into two error patterns:
  - **7 cases**: true `mel`, predicted `nv` — the single most clinically
    dangerous error mode in this dataset (melanoma missed as a benign nevus).
  - **13 cases**: true `bkl`, predicted variously as `mel`, `akiec`, or
    `bcc` — a different, less life-threatening confusion, but still
    informative about which lesion types visually overlap for the model.
- Average confidence on the 7 mel→nv failures logged in
  `gradcam_results.csv` was **~0.69** — high enough that these are
  genuinely confident mistakes, not borderline calls.
- Built `src/explain/utils.py` as shared infrastructure (image loading,
  normalization, overlay generation, model/checkpoint loading with a
  backward-compatible key remapper for older checkpoint formats) so that
  Week 5's three additional methods don't duplicate this code.

## What this means for Week 5

Grad-CAM alone answers "is the model looking at the lesion in *this*
case?" but not whether that holds up across attribution methods that
work differently (gradient-based vs. perturbation-based). Week 5 adds
saliency, Integrated Gradients, and occlusion on the same cases and
builds one harness to compare all four side by side.

## Update (Week 6) — Migration to ResNet-50 v12recipe

Per supervisor direction (see `week3.md` update and `README.md`'s Parallel
Track), the project's official checkpoint moved from `v0.1-baseline`
(ResNet-18) to `resnet50_v12recipe` (epoch 14, val_bal_acc 0.8010,
**test_bal_acc 0.7496**) starting Week 6. Since Grad-CAM's failure/correct
case selection depends entirely on which model made the predictions, all
Week 4 target-selection and heatmap generation had to be regenerated
against ResNet-50's own predictions rather than reused from ResNet-18.

### What changed in the target-selection methodology

The original 20-case list (7 mel→nv + 13 bkl-family, from
`xai_target_cases.json`) was the *N highest-confidence wrong predictions
across any class*, generated by `failure_analysis.py`. During the ResNet-50
migration, a second, more targeted script (`select_week4_targets.py`) was
adopted as the primary source for Grad-CAM and all downstream methods: it
produces two purpose-built files —

- `xai_targets_incorrect_melnv.json` — **only** mel→nv failures (the single
  clinically dangerous error mode identified in `week3.md`), sorted by
  confidence, all 10 cases where ResNet-50 makes this specific mistake
- `xai_targets_correct.json` — up to 3 confidently-correct cases per class
  (21 max across the 7 classes; 20 obtained), so the "correct" gallery is
  balanced across all lesion types rather than whatever the raw prediction
  order happened to surface

This is a deliberate narrowing from Week 4's original scope (any
high-confidence error) to a specifically mel→nv-focused audit — more useful
for the paper's clinical-risk narrative, at the cost of no longer having
bkl-family failures in the primary Grad-CAM gallery. `xai_target_cases.json`
still exists and is still regenerated by `failure_analysis.py` (now also
pointed at `resnet50_v12recipe`) for anything that wants the broader,
unbalanced failure set.

### Bugs found and fixed during regeneration

Two separate bugs surfaced while getting ResNet-50's target-selection and
Grad-CAM results to agree with each other, worth recording since both are
the kind of silent, plausible-looking-output bug that's easy to reintroduce:

1. **Class-index/label mismatch.** `select_week4_targets.py` and
   `failure_analysis.py` each hardcoded their own `CLASSES` list. One used
   alphabetical order (`akiec, bcc, bkl, df, mel, nv, vasc`); the model's
   real label encoding (`dataset.py`'s `CLASS_MAP`) is
   `mel:0, nv:1, bcc:2, akiec:3, bkl:4, df:5, vasc:6`. Whenever these two
   orderings disagreed, `true_label`/`pred_label` strings written to the
   JSON files were simply wrong for whichever index positions differed.
   Fixed by deriving `CLASSES` from `dataset.py`'s `CLASS_MAP` directly in
   every script (`failure_analysis.py`, `select_week4_targets.py`,
   `utils.py`) instead of hardcoding a second copy of the list anywhere.
2. **Image preprocessing mismatch.** `utils.py`'s `load_image()` (used by
   `gradcam.py` and every other attribution method) resized images with a
   plain `Resize((224, 224))`, which squashes/distorts the aspect ratio.
   The actual test-set evaluation pipeline in `dataset.py` uses
   `Resize(255) → CenterCrop(224)`, which preserves aspect ratio. For
   borderline-confidence cases, the distorted input was enough to flip the
   model's prediction relative to what target-selection had recorded —
   observed directly as 3 of 10 mel→nv "failure" cases showing as correct
   when re-run through `gradcam.py`. Fixed by having `load_image()` call
   `dataset.py`'s own `get_transform(split='test')` instead of a separate,
   drifted copy of the resize logic. Verified by rerun: 3/10 → 0/10.

### Updated results (ResNet-50 v12recipe)

- Ran Grad-CAM on `resnet50_v12recipe` (epoch 14, val_bal_acc 0.8010),
  producing **10 heatmaps** for the mel→nv failure list and **20 heatmaps**
  for the balanced correct-case list, split into
  `results/xai/gradcam/failures/` and `results/xai/gradcam/correct/`.
- After both fixes above, **0/10** mel→nv failure cases were reclassified
  as correct on re-run — the target-selection and Grad-CAM inference paths
  now fully agree, which they did not before the fix (3/10 disagreed).
